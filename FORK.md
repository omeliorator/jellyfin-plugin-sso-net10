# FORK.md — why this fork exists

Base: `9p4/jellyfin-plugin-sso` @ `f1e157bac29e6d27a0844378f3e1d4a4fdaa577a`
(archived head, 2026-05-12). Upstream is archived; this repository carries the
minimum change needed to run the plugin on **Jellyfin 12.4 (.NET 10)**.

Version **4.1.1.0** is deliberately distinct from
`flyzstu`'s `4.1.0.1` so a `meta.json` or a `.version-` marker can never be
confused with that binary. See `DES-007-jellyfin-12-sso-auth.md` §10 (cite the
filename — `DES-007` alone is allocated twice in the vault).

## What we changed, and why

| Change | Reason |
|---|---|
| `net9.0` → `net10.0` (both project files) | Jellyfin 12.x runs .NET 10 (12.4.0 ships 10.0.14) |
| `Jellyfin.Controller` / `Jellyfin.Model` `10.11.0` → `12.4.0`, `ExcludeAssets="runtime"` | compile against the **exact** runtime we deploy: an ABI break becomes a compile error instead of an assembly-load failure after rollout. `ExcludeAssets="runtime"` keeps Jellyfin's assemblies out of the artifact. |
| drop `System.Security.Cryptography.Xml` 6.0.1 | it is in-box in `Microsoft.AspNetCore.App` 10.0.14 (verified: the built DLL resolves, and the package does not appear in `project.assets.json`) — upstream package would pin an older out-of-band copy |
| `Newtonsoft.Json` 13.0.3 → 13.0.4 | current patch release |
| `WebResponse.cs`: web `appVersion` `"10.8.0"` → `"12.4.0"` | the only C# change the port needs; the embedded JS identifies itself to the server as Jellyfin Web |
| `AssemblyVersion`/`FileVersion` `4.0.0.4` → `4.1.1.0`; `build.yaml` `version`/`targetAbi`/`framework` | artifact identity, `targetAbi 12.0.0.0`, `framework net10.0` |

No API adaptation was required. No UI change is included: the `7669e54b5f`
sidebar commit (`SSO设置`) in `flyzstu` is **not** part of this fork.

## Deliberate differences from `flyzstu` 4effad92

1. Jellyfin packages `12.4.0`, not `12.2.0` (compile against the deployed runtime).
2. `WebResponse.cs` appVersion `12.4.0`, not `12.2.0`.
3. Version `4.1.1.0`, not `4.1.0.0`.
4. `SSO-Auth/Lib/Lib.fsproj` keeps its CRLF line endings; only the TFM line
   changes. `4effad92` rewrites the whole file, turning a one-line change into a
   26-line diff.
5. Artifact packaging is ours (`scripts/build.sh`), not JPRM, and `meta.json` is
   generated by `scripts/gen_meta.py` so the manifest is reviewable in-tree.

## Building

```bash
bash scripts/build.sh        # -> dist/sso-authentication_4.1.1.0.zip + .sha256
bash scripts/verify_artifact.sh   # gate checks (contents, meta.json, TFM, versions)
```

CI: `.github/workflows/build.yml` (ubuntu-latest, .NET 10 SDK) runs both and
uploads the zip + sha256. The sha256 that is pinned in git lives in
`artifacts/`; nothing is fetched from the publisher at runtime.

## Workflows removed from the fork

`publish.yml` and `publish-nightly.yml` published GitHub releases from this
repository and rewrote `build.yaml` on every push to `main`. This fork is not a
release channel: the artifact is built by `build.yml` and consumed by pinning its
sha256. `dotnet.yml` is retargeted to .NET 10.

## Installation contract (Jellyfin side)

Directory-scan plugin, installed at `/config/plugins/SSO-Auth/`; the config file
stays at `/config/plugins/configurations/SSO-Auth.xml` (`SSOPlugin.Name` is the
literal `SSO-Auth`). OIDC redirect path is unchanged: `/sso/OID/redirect/<provider>`.

## CI jobs

`build.yml` is the only job that matters (build + gate checks + artifact
upload). `dotnet.yml` is retargeted to .NET 10 and builds the solution.
`prettier.yml` (upstream's documentation-formatting lint) is removed: this fork
is not upstream's docs pipeline and its only finding was FORK.md's formatting.
`publish.yml` / `publish-nightly.yml` are removed: nothing is published from here.
